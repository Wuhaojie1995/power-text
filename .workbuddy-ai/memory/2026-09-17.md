## 登录页加动态背景（用户反馈「太素了，背景能不能动」）

- 背景改成三层叠加：渐变底 + 5 个缓慢漂移的彩色光斑（blur 70px）+ 细网格。
- 光斑用 `i:nth-child(n)` 分别给位置/尺寸/颜色，并错开 `animation-duration`（28~38s）
  与 `animation-delay`（负值，让初始相位不同），两组 keyframes（blob-a / blob-b）交替用，
  避免五个光斑「一起动」显得机械。
- 网格用 `::after` + 两组 linear-gradient 画线，`mask-image: radial-gradient(...)`
  让边缘淡出，再让它 46s 平移一格（44px）循环，正好无缝衔接。
- 卡片改成半透明白 + `backdrop-filter: blur(16px) saturate(150%)` 毛玻璃，
  让背后光斑透出来形成层次；品牌区渐变用 `background-size: 240%` + `background-position`
  做流动动画；logo 轻微上下浮动；提交按钮 hover 时渐变流动。
- **一个关键坑**：卡片入场动画（login-card-in）**不能写 `animation-fill-mode: both`**，
  否则动画结束后 transform 仍被动画控制，`:hover` 的位移会被盖住。
  保持默认 `none`，动画结束 transform 回到声明值，hover 才生效。
- 无障碍：`@media (prefers-reduced-motion: reduce)` 下所有动画关闭、hover 位移取消。
- 层级：`.login-bg` z-index:0 + `pointer-events:none`（纯装饰不挡点击），卡片和页脚 z-index:1。
- 验证：tsc 零错误；dev + prod 构建通过；产物里 7 个 @keyframes 全部存在、
  层级与 animation 属性正确；dev server 三个路由 200。
- 未做视觉截图：`agent-browser` 未安装（要额外下 ~500MB Chromium），本次没为纯样式改动装它。

## 登录页背景第二版：光斑 → 网格流光（用户反馈「五个彩色光斑不好看，要更炫酷的」）

- 结构从「5 个裸 `<i/>` 光斑」改成 5 个具名层：
  `.login-bg-glow`（静态四角光晕 + 暗角）→ `.login-bg-grid`（细网格）→
  `.login-bg-lines`（4 道横向光束）→ `.login-bg-cols`（4 道纵向光束）→ `.login-bg-sweep`（斜向扫光）
- 光束实现要点：`i` 元素铺满整行/整列，真正的「光」是 `background-image` 渐变（宽 30%），
  用 `background-position` 从 -30% 扫到 130%（背景图 30% 宽时可用行程 = 100%-30% = 70% 屏宽）。
  不需要额外伪元素，也不用改 JS 就能加/减光束条数。
- 共用形状抽成 Less mixin `.login-beam-shape(@deg, @head, @tail, @halo)`，配合 `fade()` 控透明度。
- **浅色底的硬限制（重要结论）**：浅背景上「发光」效果天然吃亏。试过两种都翻车：
  ① 芯部 100% 不透明 → 细线变成一道硬划痕；② 加 `filter: blur(1.4px)` → 竖线糊成灰渍。
  最终解：3px 厚 + 芯部压到 72% 不透明 + 单层 `drop-shadow` + 慢衰减拖尾。
  结论：想真正「炫酷」得上深色底，浅色底只能做到「干净克制」。
- 每层用不同 `animation-duration`（7/9.5/8.2/11s）和负 `animation-delay` 错开相位，
  避免所有光束同时到达形成「整排闪烁」。
- `prefers-reduced-motion` 下：动画关掉，并且把 lines/cols/sweep 直接 `display: none`
  —— 停下来的光带是几道僵住的亮条，比不显示更突兀。
- 验证：tsc 零错误；dev 构建通过；产物里 4 个新 @keyframes 各命中 2 次，
  旧的 `login-blob-a/b` 归零，`nth-child(4)` 命中 2 次。

- 登录页整屏深色，但 React 要等 1.4MB 的 JS 下载解析完才挂载，这期间 `<body>`
  按默认白底渲染 → 明显白屏闪一下（浅色时代两版都是白的，看不出来，改深色后暴露）。

## 收尾验证：修掉一个自己写的真 bug + 补齐无障碍分支

### Bug：切换背景第二次必挂（本次自己踩的）

- 现象：从星场切到星际穿越，控制台报
  `TypeError: Cannot read properties of null (reading 'precision')`，
  调用栈 `getMaxPrecision → new WebGLCapabilities → new WebGLRenderer`。
  页面表现是「切了没反应」——因为容错逻辑 warn 后回落到静态背景，所以没崩。
- 根因：`ThreeBackground` 的 canvas 常驻 DOM（React 不重建它），
  而 `dispose()` 里调了 `renderer.forceContextLoss()`。
  **WebGL 规范规定同一个 canvas 上 `getContext()` 永远返回首次创建的那个对象**，
  上下文丢失后只会返回那个已丢失的 context（甚至 null），不会新建 ——
  于是第二次 `new WebGLRenderer({ canvas })` 拿到 null，当场抛错。
- 修法：给 canvas 加 `key={`${background}:${active ? 'on' : 'off'}`}`，
  让每次需要 WebGL 的组合都拿到全新的 canvas 元素。
  `three-scene.ts` 的 `forceContextLoss()` 处加了交叉引用注释，避免以后有人单独删掉其中一个。
- 验证：连切 4 次（星场→穿越→星云→星场）+ 深浅主题来回切，控制台零错误，每次都正常渲染。

### 无障碍分支补齐

- 原来 `webglActive` 只判断「背景是 3D + 深色主题」，没管 `prefers-reduced-motion`。
  后果：开了「减少动态效果」的用户，`has-webgl-bg` 类照样加上，
  CSS 的网格/光束层被 `display:none` 关掉，而 WebGL 又不启动 → **看到一片几乎空白的深色页**。
- 修法：新增 `usePrefersReducedMotion()`（state + matchMedia 监听 change，实时响应），
  把 reduced-motion 纳入 `webglActive`。条件不满足时 `has-webgl-bg` 不加，
  页面干净回落到静态 CSS 背景（网格 + 光晕，不动但仍有层次）。
  `ThreeBackground` 里保留 matchMedia 检查作为双保险。
- 验证：用 CDP 的 `Emulation.setEmulatedMedia` 模拟 reduce →
  `pageClass` 是 `login-page`（无 has-webgl-bg）、canvas 保持 300×150（three 未加载）、
  页面显示静态网格背景。

## 运行时行为验证：数 draw call 与 RAF 次数

截图只能证明「画面对不对」，证明不了「机制有没有生效」。代码里写了三个运行时机制
（限帧 30、页面隐藏暂停、卸载释放显存）但一个都没验过，这次用注入探针数调用次数验完了。
脚本：`.workbuddy-ai/preview/login-bg/verify-runtime.mjs`。

**探针做法**（走 `Page.addScriptToEvaluateOnNewDocument`，必须早于页面自身脚本）：

- 包装 `WebGLRenderingContext` / `WebGL2RenderingContext` 原型上的
  `drawArrays / drawElements / drawArraysInstanced / drawElementsInstanced` 计数
- 包装 `HTMLCanvasElement.prototype.getContext` 统计创建了几个上下文，
  并给每个 canvas 挂 `webglcontextlost` 监听统计丢失数
- 包装 `window.requestAnimationFrame` 统计回调**真正被执行**的次数

**关键技巧**：RAF 计数是用来区分「限帧生效」和「环境本身就慢」的。
只测帧率的话，软渲染下不管怎么调都停在 22fps 左右，根本判断不出限帧有没有用；
必须同时看 RAF 频率和渲染帧数的**比值**。

### 验证结果（headless + SwiftShader）

| # | 项目 | 结果 | 判定 |
|---|---|---|---|
| 1 | 全屏渲染 | 23.3 fps | 正常（软渲染瓶颈，判断不了限帧） |
| 2 | 页面隐藏 2s | **0 次 draw call** | 暂停生效 |
| 3 | 恢复可见 2s | 47 次 | 恢复生效 |
| 4 | 连切 13 次背景 | 创建 13 个上下文、丢失 12 个 | **无泄漏** |
| 5 | 切换后渲染 | 23.0 fps | 没被玩坏 |
| 6 | RAF vs 渲染 | RAF 60.0 fps / 渲染 22.3 fps，比值 2.69 | **限帧生效** |

页面错误：无。

第 4 条最重要：如果 dispose 不彻底，用户切十几次背景就会耗尽浏览器的 WebGL 上下文配额，
页面直接黑掉 —— 这类问题只有数计数才看得出来。

第 6 条的推理过程值得记：缩到 420×280 帧率纹丝不动（22.8 → 22.7），
说明瓶颈不是像素填充；换成顶点少 4 倍的 warp 场景也一样。
最后靠 RAF 计数才定性 —— RAF 跑满 60fps 而渲染只有 22.3fps，比值 2.69 而非 1.0，
证明每帧并非都在渲染，限帧确实在起作用。
（比值不到整 2 是因为软渲染下 RAF 时间戳不均匀，不影响结论。）

## 第四轮：三套 3D 背景全部重做（用户否掉了「安静氛围型」）

### 判断
用户原话：「【深空星场，星际穿越，星云雾海】这三种也不炫酷，换了」。
先承认问题本质：那三套是**低对比、低饱和、动势柔和**的「安静氛围型」，
本质上就是「一屏缓慢移动的柔光」——那不叫炫酷，叫耐看。
调参救不了，得换配方。新配方四条：**强透视结构 + 高饱和霓虹 + 明确动势 + 辉光后处理**。

### 换掉的三套

| `hypergrid` | 霓虹地平线 | 网格地面朝观众飞驰（位移对格长取模实现无缝循环）+ 3 条扫过的光带 + 地平线上的条纹太阳 + 天幕星点 |
| `hyperjump` | 光速跃迁 | 90 个六边形能量环 + 44 个细圆环（InstancedMesh + 逐实例色）冲向镜头 + 光尘 + 尽头亮核，每 8 秒一次高斯冲刺 |

### 外壳加了辉光后处理（`three-scene.ts`）
- `SceneInstance` 新增可选 `bloom?: BloomOptions`，场景声明即启用；
  不声明就走原来的 `renderer.render()`，不付后处理的钱
- 四个 pass（EffectComposer / RenderPass / UnrealBloomPass / OutputPass）**全部动态 import**，

- `OutputPass` 不能省：离屏渲染不会自动做色彩空间转换，少了它整屏发暗发灰
- 顺序改成「先 createScene → applySize → 再建 composer」，composer 一出生就是正确分辨率
- dispose 里显式 `bloomPass.dispose()` + `composer.dispose()`，renderer.dispose() 管不到那些 render target

### 翻车记录：加法混合的亮度预算（来回调了三轮）
1. **第一版整屏糊成白**：环数量多 + 每环亮度 1.8 + 贴到镜头前覆盖全屏，累加直接饱和。
2. **压过头变成全黑**：亮度降到 0.5 又太暗，什么都看不见。
3. **最终三件套**（缺一不可）：
   - 单物体亮度压到 ~0.6~1.4（看物体数量定），不要贪大；
   - **靠近镜头的按距离淡出**（`proximityFade`），绝不让它整个罩住屏幕；
   - **远端也淡入**（`farFade`）——消失点处几十个物体的投影挤在同一小块，不淡入必然烧白；
   - 辉光 `threshold` 抬到 0.2~0.3，`strength` 从 0.7 起步。
4. **太阳的条纹看不见**：加法混合下「暗带」等于「不加光」，周围光晕糊过来就填平了。
   改成**普通混合**（`transparent: true`，不写 blending）让圆盘真正遮挡，条纹立刻出来。
   顺带把 `depthWrite` 打开 + `renderOrder = -1`，后面的星点才会被太阳挡住；
   条纹保留 1.5% 不透明（完全透明的话那块不写深度，星星会从缝里透出来）。

### 翻车记录：构图（代码全对，但截图前发现不了）
登录卡片占画面正中 660×290。**任何居中的主体都会被整块盖住**：
- 第一版太阳放正中 → 只在卡片边上漏一圈光晕，圆盘和条纹全看不见；
- 漩涡中心放正中 → 最亮的光核整个被卡片吃掉。
解法：**绕相机自身轴 `rotateY` / `rotateX` 把主体推到卡片之外**。
换算：`屏幕偏移 = 中心 + (偏转角 / 半视场角) × 半屏宽`。
最终太阳推到卡片右侧（rotateY 不需要，直接改世界坐标 x=980），漩涡用 rotateY(0.42) + rotateX(-0.12)。

### 另一处连带修复
`has-webgl-bg` 下卡片白度从 0.86 提到 0.94。3D 背景里最亮的地方（太阳、光核）
亮度远高于原来那层 CSS 光晕，14% 的透光会把底色带上来、把白色表单染成粉的。
投影也换成更深的 `rgba(2,6,23,0.45)`。

### 验证结论（`verify-runtime.mjs` 重写后）
探针的帧数口径连错两次，最后定在 `bindFramebuffer(target, null)`：
- `drawArrays` 不行：每帧 draw call 数随场景变（单 Points 是 1，7 个 Sprite 是 8）；
- `gl.clear` 不行：加了后处理之后**每个 pass 都 clear 一次**，一帧十几次，
  实测算出 318fps 这种明显不可能的数；
- `bindFramebuffer(null)` 每帧恰好一次，有没有后处理都成立。

实测结果（全绿）：

- 缩到 420×280：渲染 23.7fps vs RAF 60.3fps，**比值 2.55 → 限帧 30 生效**；
  帧间隔中位数 48.6ms（≥33.3ms 判据）
- 页面错误：无
- 浅色主题 / reduced-motion：`pageClass` 分别是 `login-page is-light` 和 `login-page`，

## 第五轮：三套 3D 背景再次全部重做（「脑洞放大 + 光污染不严重 + 必须有星空」）

用户原话：「这三个特效不行，再换，脑洞放大嘛！要炫酷得，光污染不严重得，新处理得特效有一个星空就行，其他几个换成其他特效，」

### 设计判断
上一轮三套（霓虹地平线 / 光速跃迁 / 能量漩涡）被否的通病是「加法混合往上堆亮度」——
整屏高饱和亮色块。本轮把轴反过来：**亮度高 + 面积小 = 炫；亮度高 + 面积大 = 光污染**。
暗部占 90%+，发光面积压到几个百分点，靠形态、深度、运动取胜。

### 新三套
1. **深空星场**（starfield.ts）三层视差星点（1400 / 2600 / 4200，各自绕视线轴以不同角速度自转）
   + 银河带 + 十字星芒主角星 14 颗 + 流星池 3 颗。
   相机**平移**而非旋转——旋转等于转天球，三层一起动，视差就没了。
2. **引力透镜**（lensing.ts）全屏 quad + fragment shader 实时算偏折：`warpedR = r - k/r`，
   `r = √k` 处采样半径归零，正是视界半径。吸积盘必须在**偏折后**的坐标里判断，
   盘面才会自己绕到视界后面、在洞顶形成那道弧。多普勒不对称是「盘在转」的唯一视觉证据。
3. **光织**（weave.ts）320 根细丝 × 110 采样点 = 69760 顶点，位置全在顶点着色器算。
   扭转速率**随半径递减**是「织」和「拧」的分界（速率一致则所有丝平行推进，只是一根麻花）。

被放弃的第四方案：**粒子潮汐**（tide.ts，五万粒子铺成夜海）——两轮调整后仍不够密，
根因是地面平面均匀撒点、近端视场宽远端窄，同一粒子数两头不可能都够密。归档 round3。

### 本轮踩的坑（六个真实 bug）
- 星场第一版几乎全黑：尺寸分布 `pow(random, 3.0)` 把多数点压到 0.55 倍基尺寸（约 0.8px），
  亚像素点被光栅化直接抹掉。尺寸下限提到 0.7 倍、亮度下限 0.18→0.32、fragment 指数 3.2→2.6
- 星芒看不见：臂宽系数 34 → 臂不到 1px 被抗锯齿抹平，改成 12（约 1.5~2px）
- lensing.ts 注释里的反引号截断模板字符串 → Vite 500、动态 import 失败、canvas 退回 300×150
- 引力透镜出现等间距斜条纹：排查走了四层（hash 退化 → pow 负数 UB → 二分关模块 → Node 复算），
  **根因是 `clamp(warpedR, -1.2, 1.2)` 夹在可视范围内**（16:9 四角 r 就有 0.94，21:9 到 1.27），
  所有 r > 1.2 的像素被映射到同一个圆上。顺带修掉 hash 整数退化与 `pow` 负数两处隐患。
  另外**排查脚本自己也错过一次**，教训是先自证脚本正确再下结论
- login.less 卡片透明度笔误 `0.14`（应为 `0.94`）→ 卡片变毛玻璃，背景细丝全透出来。
  用 `getComputedStyle` 读到 `cardBg` 才定位；中途一次「仍透」是 Less HMR 未生效的中间态
- 光织左上角烧出白核：丝束远端在屏幕上压缩成很小一块，几百根丝加法叠加。
  `endFade` 远端淡出起点 0.72 → 0.35、辉光降到 0.55/0.45/0.45，确认无白核后亮度回提到 `(0.3 + 0.62 * pulse)`
